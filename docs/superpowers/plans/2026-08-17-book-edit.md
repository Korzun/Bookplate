# Step 7 — Book edit Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move `page/book-edit` and `BookEditForm` entirely onto GraphQL — reads via a new
`BookEditDocument`, Save via `bookUpdateMetadata` with the cover staged first.

**Architecture:** A new reusable client staging module posts cover bytes to the permanent REST
staging seam and returns a staged id; a mutation hook orchestrates stage-then-mutate and evicts the
old cache entity when the content hash changes; the page and form are rewired together in one task
because the form's props change shape.

**Tech Stack:** Apollo Client v4 + `client-preset` codegen with **fragment masking ON**;
graphql-yoga + Pothos v4 + Prisma server-side; vitest + `@testing-library/react`.

**Spec:** `docs/superpowers/specs/2026-08-17-step7-book-edit-design.md`

```ts
// app/client/src/lib/staged-upload.ts
import { apiFetch } from '~/lib/api-fetch';

const ROUTES = {
  cover: '/api/books/cover-staging',
  epub: '/api/books/replace-staging',
} as const;

/** The multipart field name each route's multer instance expects. */
const FIELD = { cover: 'cover', epub: 'file' } as const;

export type StagedKind = keyof typeof ROUTES;

/**
 * Posts bytes to the REST staging seam and resolves the staged upload id.
 *
 * Staging is a PERMANENT REST seam (apollo-client-migration spec §9.1): it is
 * multipart, and GraphQL has no transport for file bytes here. The GraphQL
 * mutations take the returned id instead — `bookUpdateMetadata`'s
 * `stagedCoverId`, `bookReplace`'s staged epub id.
 *
 * Parameterised by kind because step 9's replace flow needs the identical
 * shape against `replace-staging`; this is the first client staging helper in
 * the codebase, so it is built once rather than inlined at the call site.
 *
 * The server gives a staged upload a 30-minute TTL with a lazy sweep and a
 * one-time `consume` (`services/replace-staging.ts`), so bytes staged for a
 * mutation that then fails clean themselves up — callers need no compensation.
 */
export async function stageUpload(
  file: File,
  kind: StagedKind,
  withTargetUser: (url: string) => string = (url) => url
): Promise<string> {
  const body = new FormData();
  body.append(FIELD[kind], file);

  const response = await apiFetch(withTargetUser(ROUTES[kind]), { method: 'POST', body });

  if (!response.ok) {
    let message = `Failed to upload the ${kind === 'cover' ? 'cover image' : 'file'}`;
    try {
      const parsed = (await response.json()) as { error?: string };
      if (parsed.error) message = parsed.error;
    } catch {
      // Non-JSON body (e.g. a proxy error page) — keep the generic message.
    }
    throw new Error(message);
  }

  const { stagedUploadId } = (await response.json()) as { stagedUploadId: string };
  return stagedUploadId;
}
```

**Interfaces:**
- Consumes: `BookUpdateMetadataDocument`, `stageUpload` (Task 1), `provider/apollo/unwrap-result.ts`.
- Produces:
  ```ts
  export type BookEditPatch = Partial<{
    title: string; titleSort: string; author: string; authorSort: string;
    description: string; publisher: string; publishDate: string;
    series: string; seriesIndex: number; subjects: string[];
    identifiers: { scheme: string; value: string }[];
    cover: File;
  }>;
  export type UpdatedBook = { id: string; documentId: string };
  export const useUpdateBookMetadata: () => [
    (bookId: string, patch: BookEditPatch) => Promise<UpdatedBook | undefined>,
    boolean,            // saving
    string | undefined, // errorMessage
  ];
  ```
  **A deliberate 3-tuple, where the four sibling mutation hooks are 4-tuples**
  (`[fn, loading, error, errorMessage]`). Those carry a separate boolean `error` beside the message
  because their callers branch on it; `BookEditForm` only ever renders the message, so a bare
  `error: boolean` would be a field nothing reads. Say so in the hook's doc comment, so the
  divergence reads as a decision rather than an oversight.

**The four existing mutation hooks are one convention** — `use-delete-book.ts`,
`use-regen-chapters.ts`, `use-validate-book.ts`, `use-clear-book-editions.ts`. Read one before
writing: same `Extract<NonNullable<…>, {__typename}>` payload alias, same `if (saving) return`
guard, same `try/catch/finally`, same `unwrapResult` `missing`/`error`/`ok` ladder, same `useMemo`'d
tuple. Match it.

**The two things unique to this hook:**

1. **Stage the cover FIRST, and only if it changed.** A staging failure must NOT fire the mutation,
   and its message must be distinguishable from a save failure — "couldn't upload the cover image"
   and "couldn't save your changes" are different problems for the user, and today's single
   multipart request cannot tell them apart.
2. **Evict the old entity when the id changed.** A metadata edit rewrites the file, so the content
   hash — and therefore the Relay global id — can move. This is the same conditional eviction
   `use-regen-chapters.ts` already implements; read it.
